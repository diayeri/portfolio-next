웹 UI를 만드는 일을 설명하다 보면 비슷한 단어가 반복해서 등장합니다. 마크업, 웹 퍼블리싱, UI 개발, 프론트엔드 개발. 회사마다 부르는 이름도 다르고, 한 사람이 여러 역할을 맡는 경우도 많습니다.

엄격한 직무의 경계를 나누기 위함은 아닙니다. 다만 실무에서 역할을 구분할 때 기준이 되는 지점이 무엇인지, 그리고 제가 어떤 과정을 거쳐 UI를 만드는 범위를 넓혀왔는지를 기록했습니다.

## 01. 비슷해 보이지만, 조금씩 다릅니다

역할의 범위는 대략 다음과 같이 넓어집니다.

```text
마크업
  ↓
웹 퍼블리싱
  ↓
UI 개발
  ↓
프론트엔드 개발
```

다만 이것은 더 높은 직무로 올라가는 계단이 아닙니다. 역할의 범위가 달라질 뿐이고, 프로젝트와 조직에 따라 경계는 얼마든지 달라질 수 있습니다.

### 마크업: HTML 구조를 만드는 일

마크업은 디자인을 HTML 구조로 표현하는 일입니다. 콘텐츠의 의미에 맞는 태그를 선택하고, 시맨틱 구조와 웹 접근성을 고려합니다.

로그인 화면이라면 `form`, `label`, `input`, `button`을 사용해 사용자가 이해할 수 있는 구조를 만드는 것이 핵심입니다. CSS가 화면을 보기 좋게 만들 수는 있지만, 마크업의 출발점은 **콘텐츠와 구조**입니다.

### 웹 퍼블리싱: 디자인을 실제 웹 화면으로 구현하는 일

웹 퍼블리싱은 마크업보다 넓은 범위를 다룹니다. HTML과 CSS를 기반으로 디자인 시안을 실제 브라우저 화면으로 구현하고, 반응형 레이아웃과 기본적인 인터랙션까지 연결합니다.

PC와 모바일에서 레이아웃이 달라지거나, 메뉴가 열리고 닫히거나, 스크롤에 따라 헤더가 변하는 동작도 퍼블리싱의 결과물에 포함될 수 있습니다.

> 참고로, '웹 퍼블리싱(Web Publishing)'과 '웹 퍼블리셔'라는 직무명은 주로 한국과 일본 등 동아시아권 IT 업계에서 디자인과 마크업/UI 구현 영역을 명확히 분리하기 위해 고유하게 정착된 호칭입니다. 영미권 글로벌 시장에서는 주로 **Markup Developer**, **UI Engineer**, 혹은 **Front-End Developer (Markup/Styling 중심)** 등의 표현으로 통용됩니다.

### UI 개발: 재사용 가능한 UI 구조를 만드는 일

UI 개발에서는 페이지 하나를 완성하는 것에서 더 나아가 **UI를 어떻게 구조화하고 재사용할지** 고민합니다.

버튼 하나를 만들더라도 특정 페이지에만 존재하는 스타일로 끝내는 것이 아니라, 상태와 크기, 사용 맥락을 고려한 컴포넌트로 만들 수 있습니다. 여러 화면에서 반복되는 UI를 컴포넌트로 분리하고, 공통 패턴을 정리하고, Storybook이나 디자인 시스템으로 문서화하는 일도 여기에 포함됩니다.

```text
페이지를 만든다
        ↓
UI를 컴포넌트로 나눈다
        ↓
공통 패턴을 정리한다
        ↓
디자인 시스템으로 확장한다
```

### 프론트엔드 개발: 제품이 실제로 동작하게 만드는 일

프론트엔드 개발은 UI를 포함해 **사용자의 행동에 따라 제품이 동작하는 과정**을 다룹니다. 데이터와 상태를 관리하고, API를 연동하고, 폼과 인증, 라우팅, 에러 처리와 성능까지 고려합니다.

상품 페이지를 예로 들면 상품 정보를 불러오고, 옵션을 선택했을 때 가격을 바꾸고, 로그인 여부를 확인하고, 주문 API를 호출하고, 성공과 실패 결과를 화면에 보여주는 일까지 프론트엔드의 범위입니다.

## 02. 웹 퍼블리싱과 디자인에서 시작했습니다

저는 웹디자인과 퍼블리싱으로 커리어를 시작했습니다. 디자인을 화면으로 옮기기 위해 HTML, CSS, JavaScript와 jQuery를 사용했고, 반응형 레이아웃과 실제 서비스의 인터랙션을 구현했습니다.

Makewith와 밀알복지재단에서의 경험은 **디자인 의도를 이해하고 웹 화면으로 구체화하는 과정**에 가까웠습니다. 화면의 완성도뿐 아니라 콘텐츠의 우선순위와 사용자가 정보를 읽는 흐름도 함께 고민하게 되었습니다.

밀알 후원 결제 프로젝트에서는 직접 코드를 작성하는 것보다 **문제를 발견하고 UX를 설계하는 일**이 중심이었습니다. 후원자 유형에 따라 입력 구조를 나누고, 결제 과정을 단계적으로 재배치하고, 외부 개발사와 구현 결과를 QA했습니다.

## 03. UI를 만들면서 정리에 진심이 되었습니다

React를 사용하면서 화면을 단순히 구현하는 것보다 **UI를 어떻게 구조화하고 재사용할 것인지**에 관심을 갖게 되었습니다.

Klaybay와 Chromatic에서는 React와 TypeScript를 기반으로 UI를 개발하고, 반응형 화면과 공통 컴포넌트를 관리했습니다. 정적인 마크업을 전달하는 방식에서 컴포넌트 단위로 UI를 만들고 Storybook으로 상태를 확인하는 방식으로 확장했습니다.

특히 여러 화면에서 반복되는 UI를 컴포넌트 단위로 정리하고, 필요한 화면을 조합해서 만들어갈 수 있게 되었을 때 큰 성취감을 느꼈습니다. 처음에는 하나의 화면을 만드는 일이었다면, 점점 여러 화면을 효율적으로 만들어낼 수 있는 구조를 만드는 일에 흥미를 느끼게 되었습니다.

## 04. 프론트엔드로 영역을 넓혔습니다

이스트소프트 프론트엔드 부트캠프를 통해 항상 거대하게만 느껴졌던 프론트엔드의 세계를 기초부터 다시 다지기 시작했습니다. 치열하게 공부한 끝에 우수 수료라는 좋은 결과로 이어졌고, 이것이 자연스럽게 이스트소프트에서의 인턴십 기회로 연결되었습니다.

실무 환경에서 데이터를 연결하고, 화면에 동적으로 보여주며, 유지보수성을 고려해 코드를 정돈해 나가는 과정은 저에게 또 다른 큰 즐거움이었습니다.

이스트소프트 Rounz에서는 사용자 화면과 운영 시스템의 UI를 개발하고, 데이터 기반의 화면과 기능을 다뤘습니다. 이후 개인 포트폴리오를 만들면서는 Next.js, TypeScript, MDX, 반응형 레이아웃과 배포까지 직접 연결했습니다.

## 05. 그래서 지금은 이렇게 일합니다

저의 주된 관심사는 여전히 **사용자에게 보이는 경험과 UI**입니다. 데이터와 기능을 다루더라도 결국 사용자가 이해하고 사용할 수 있는 화면으로 연결되어야 한다고 생각합니다.

저는 디자인과 개발 중 하나를 선택하기보다, 사용자에게 보여지는 경험을 설계하고 그것을 실제 제품으로 구현하는 과정에 가장 큰 흥미를 느끼고 있습니다.

이처럼 웹디자인과 퍼블리싱에서 시작해 UX/UI 디자인, UI 개발, 프론트엔드까지 경험의 범위를 넓혀왔습니다. 이 과정에서 각 역할이 완전히 분리되어 있다기보다, 서로 다른 관점으로 같은 제품을 바라본다는 것을 배웠습니다.

앞으로도 사용자의 문제를 이해하고, 좋은 UI 구조를 설계하고, 그것을 실제 서비스로 구현하는 일을 계속하고 싶습니다. 역할의 이름보다 중요한 것은 사용자가 만나는 경험을 더 나은 방향으로 만드는 것이라고 믿습니다.
